# P1.5 查询构造修复结论（fts_pg 参数绑定 + 排序方向）

- 日期：2026-09-21
- 环境：tmesh PG（geekpark-tmesh 容器）
- 对照：`eval/reports/experiments/P1_FULL_p15_*.json`

## 根因（比 `-50` 更底层）

`fts_pg.build_toks_filter` 把 score_expr 的参数和 WHERE 的参数收在**同一个列表**里，
顺序为 `filter_params + score_params`；但调用方把 score_expr 放在 **SELECT 列表**，
在 SQL 文本中**先于** WHERE。占位符按文本顺序绑定，于是整体错位：

```
期望 score 槽位: %ifa%, %编辑%, %辑部%, %部选%, %选题%, %题里%
实际 score 槽位: %ifa%, %ifa%, %ifa%, %ifa%, %编辑%, %编辑%   ← 错位
```

连带把 WHERE 的过滤词整体后移，**GROUP 1 的 `ifa` 过滤被整个丢掉**。

实证（`编辑部选题里 IFA 相关`，slug=2026-09-08）：

| 版本 | 行数 | Top1 | 分数 |
|---|---|---|---|
| 修复前 | 20 | `[Data Source] 编辑部` | 全为 `-2.000`（常数） |
| 修复后 | 1 | `[关注了什么] IFA 探展与逛展` ✓ | `-3.000` |

## 附带修复：排序方向

`ORDER BY score DESC` 与系统约定（分数越小越好，`merge_hits` 用 ascending）相反，
会在 `LIMIT` 截断时优先丢掉**最相关**的行。SQLite 分支用 `bm25` 升序，方向正确。
改为 `ASC` 后 chunk 池内命中 0.2883 → **0.3050**。

## 修复方式

`build_toks_filter` 改为返回 **4 元组** `(filt, filter_params, score_params, score_expr)`，
由调用方按 SQL 文本顺序显式拼接（`score_params + filter_params`），消除隐式顺序陷阱。
两处调用（`fts_pg.search_fts`、`item_facts.search`）同步修正。

## 结论

**保留该修复。** 它是融合层改造（RRF）的必要前提 —— 此前通道内部排序本身就是错的
（过滤条件丢失 + 排序反向），RRF 只会把错误位次按排名融合。

R12/R13 的位次变化属「分数语义修正后的重排」，非补丁造成
（quality ON/OFF 的 R@5 完全相同），留待 RRF 统一处理。
